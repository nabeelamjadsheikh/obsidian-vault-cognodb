Two hours on the phone with Andrew Mensah, most of it him arguing that Lantern does not need a graph store and does not need me to have opinions about graph stores. Provisional answer: yes it does, but for one reason rather than the six I went in with.

His position, which is a good one: a relational schema with two join tables would serve every screen currently in [[Lantern — Project Overview]], and would come with tooling, hosting and a decade of my own habits already in place. Adding a second storage paradigm to a two-person project is a real cost paid every week.

What moved him was not an argument, it was the second query in [[Lantern — Query Patterns]] — highlights connected through shared themes, excluding pairs already linked, ranked by overlap. In SQL that is a self-join with a NOT EXISTS and it is legible-ish. Extend it one hop, to themes-of-themes, and it stops being legible. That query is the product; if the thing that makes the app worth using is awkward in the storage layer, we will simply build fewer of them. He conceded the point faster than I expected, and his own longer version of the reasoning is now in [[Andrew on Graph Databases]].

The shape we settled on is written up in [[Lantern — Data Model]] — the join table becomes an annotated edge, which was his idea, not mine.

The discipline I want to keep: this is a decision we can defer cheaply by keeping the model narrow, and the correct next move is a two-day spike that answers it with data. Not a migration. [[Ship the Smallest Real Slice]] applies to infrastructure decisions too — the smallest real slice here is one query, one screen, one week.

Separately, half of what I described to Andrew as "Lantern needs this" is already solved in [[Vault Tooling — Overview]]. I should stop building the same thing twice.
